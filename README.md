# 賓果分析台（GitHub 版）

這是「賓果分析台」的完全自動化版本，用 GitHub Actions 排程 + GitHub Pages 架設，
取代之前 Claude 排程任務會卡在「等待人工核准」的問題。設定好之後**完全不需要人再點任何東西**，
也不會再消耗 Claude 的用量額度，因為抓資料、算統計、寫回、部署網頁這幾步都是純程式碼跑在
GitHub 自己的伺服器上，不經過任何 AI 或需要核准的流程。

## 這個版本改善了什麼

1. **真正自動、免費、無上限**：GitHub Actions 對公開（public）repo 完全免費、分鐘數無上限，
   排程用純 Python 發 HTTP 請求，不會跳出「是否允許存取」的核准視窗。
2. **資料來源升級**：改用 [lottery.timetable.tw](https://lottery.timetable.tw/developers)
   提供的台灣彩券公開資料 API（結構化 JSON、免金鑰、唯讀），取代原本請 AI 讀網頁、
   用文字摘要方式轉錄表格的做法——後者偶爾會摘要不完整或抓不到最新列，前者是乾淨的
   結構化資料，準確且穩定很多。
3. **頻率拉高**：從每小時一次改成每 15 分鐘一次（GitHub 排程本身在系統忙碌時可能延遲
   幾分鐘是正常現象，但比原本的每小時已經好上很多）。
4. **開獎歷史紀錄會標示命中**：每一期都用「該期之前」的歷史資料重算一次綜合建議，
   跟該期實際開獎比對，剛好命中的號碼會用綠色標示（不是用未來資料回推，是誠實的
   逐期比對）。
5. **新增兩個真正對應得上的方法**：`空間自相關法（Moran's I）`（真正的空間幾何學／
   空間統計方法）跟`共現矩陣譜分析（特徵值分解）`（真正的線性代數方法），取代原本
   有點名不符實的標籤（見下方「關於這些數學方法」）。
6. **網頁風格調整**：改成偏遊戲介面的視覺風格（號碼變成有光澤的圓形代幣、命中號碼
   會發光、標題用漸層色、卡片標題有色塊標記），但配色系統跟深色／淺色模式邏輯不變。
7. **修正「開獎時間都一樣」的問題**：實測發現 API 的 `created_at` 其實是「這批資料被
   寫進資料庫的批次同步時間」，不是逐期的真實開獎時間，同一批（十幾期）會共用同一個
   時間戳記，導致畫面上一整排不同期別顯示同一個時間。改成用「賓果賓果每 5 分鐘開一
   期」這個公開規則、搭配一個固定不變的錨點（存在新增的 `data/time_anchor.json`）反推
   每一期的時間，穩定、不會每次排程亂跳，也會一次修好過去已經算錯的歷史時間。
   **這個修正需要 `.github/workflows/update.yml` 也一起更新**（多加了一個要 commit 的
   檔案），細節見下方上線步驟。
8. **排程錯開整點/整 15 分**：`cron` 從 `*/15 * * * *` 改成 `7,22,37,52 * * * *`——
   GitHub 官方文件說整點附近是全世界排程最擁擠的時間，容易延遲甚至跳過，錯開幾分鐘
   是官方建議的降低機率做法（不保證完全不延遲）。
9. **誠實標示資料源本身的跳期**：實測發現我們用的第三方公開 API
   （lottery.timetable.tw）自己同步資料時，偶爾會整批漏掉幾期（官方台灣彩券網站
   本身沒有缺，純粹是這個第三方轉發服務弄丟的）。這不是我們抓取程式的 bug，也修
   不了（我們沒有這個第三方服務的後台），所以改成誠實面對：開獎歷史紀錄清單偵測
   到期別不連續時，會插入一行醒目的橘色提示「⚠️ 資料來源缺漏 N 期」，讓你一眼就
   知道這是已知的資料源限制，不是網站壞掉。下方所有命中率／回測統計都是照清單
   實際順序逐期比對，不依賴期別數字連續，所以這些缺漏完全不影響任何統計數字的
   正確性；「本期開獎」跟「各方法建議號碼」也一樣，永遠是用當下實際抓得到的最新
   資料現算，不會因為中間缺期就跳過或卡住。
10. **再修一次「時間跟現實對不上」的問題（這次是真的解決，不只是治標）**：上一版
    （第 7 點）把「期別 ↔ 時間」錨點做成「只建立一次、之後永久寫死」，原本用意是
    穩定、不要每次排程亂跳。結果實測發現 BINGO BINGO 晚上有一段真的會暫停開獎的
    時間（期別數字暫停期間不會前進，但現實時間照樣在走），一次寫死的錨點沒辦法
    感知這種暫停，每次暫停都會讓畫面上的時間跟實際時間多差一截、而且不會自己
    修正回來，累積幾天後就會像使用者回報的「現在都早上了，網站卻還顯示前一天
    下午」。改成：**錨點會在每次抓到「比上次更新的期別」時，自動重新校正到當下
    的真實時間**；如果這次沒抓到更新的期別（上游卡住或漏同步），就維持原本的
    錨點，不會讓時間憑空往前跳。這樣一來，只要資料還在正常更新，最新一期顯示的
    時間誤差通常只有幾分鐘，也不會再一路累積成好幾個小時。
11. **換掉不穩定的資料來源**：原本用的 lottery.timetable.tw 這個第三方公開 API，
    陸續踩到三種不同的可靠性問題——自己同步時偶爾漏掉幾期、曾經卡住好幾小時、
    最後一次是直接整整停擺將近 14 小時、上百期沒更新，同時間官方開獎跟其他獨立
    來源都正常，確認問題出在這個第三方服務本身，不是我們的程式或排程。既然
    連續出過三次狀況，就不再依賴它，改抓 [彩世界開獎網](https://988cp.net/history?g=BingoBingo)
    的即時歷史頁面（用 Playwright 無頭瀏覽器載入頁面、解析渲染後的文字取得
    期別與號碼，不採用它顯示的時間文字——時間還是用第 10 點那個自我校正的
    錨點機制推算）。這個頁面預設一次顯示最近 100 期（約 8 小時份量），比原本
    「漏了就永遠補不回來」的資料源多了很多容錯空間：就算某次排程沒跑成功，
    下一次通常還是能把中間的期數一次補齊。**這個修正需要 `.github/workflows/update.yml`
    也一起更新**（多加了安裝 Playwright 瀏覽器的步驟），細節見下方上線步驟。
    第 9 點提到的「資料來源缺漏」橘色提示功能繼續保留，當作通用的安全網——
    不管未來用的是哪個資料源，只要期別出現不連續，畫面都會誠實標示出來，
    不會又讓人誤以為網站壞了。

## 檔案說明

- `scrape.py` — 用 Playwright 無頭瀏覽器載入 988cp.net 的開獎歷史頁面，解析出最新開獎資料，合併進 `data/draws.json`（去重、依期別排序，只保留最近約一個月份的量避免檔案無限成長）；時間欄位用自我校正錨點（`data/time_anchor.json`）＋ 5 分鐘間隔推算，不採用任何外部來源的時間文字。
- `analysis.py` — 統計/回測引擎。在你原本的 7 個方法之外，新增了 2 個方法（見下方說明）。
- `build_stats.py` — 讀 `data/draws.json`，呼叫 `analysis.py` 重新計算，寫成 `data/stats.json` 給前端讀；同時算出「開獎歷史紀錄」每一期的命中標示。
- `index.html` — 儀表板本體，跟原本 Claude Artifact 版本大致一致（多方法比較、綜合建議、命中回測、星數下拉選單），差別是：改成定期用 `fetch()` 讀取同目錄下的 `data/stats.json`（而不是連 Claude 的即時資料庫）；原本的全號碼熱力圖換成「開獎歷史紀錄」清單（顯示最近 100 期，每期的期別、台灣時間、20 個開獎號碼，命中當時建議號碼的會標色）；視覺風格改成偏遊戲介面的樣子。
- `.github/workflows/update.yml` — 排程設定，每 15 分鐘自動跑 `scrape.py` → `build_stats.py` → 把有變動的檔案 commit 回 repo。
- `data/draws.json`、`data/stats.json` — 目前已經放了你原本的 10 期真實種子資料算出來的結果，一上線就有內容可看，不會是空的。

## 上線步驟（大約 5 分鐘）

1. 到 GitHub 網站，用你現有帳號（`levis50192-cmyk`）新增一個 **public**（公開）repository，
   例如取名 `bingo-analysis`（一定要是 public，private repo 排程要另外設定額度，比較麻烦）。
   建立時不要勾選「Add a README」（我們自己有帶）。
2. 把這個資料夾裡的所有檔案（包含 `.github` 這個隱藏資料夾）上傳到剛剛建立的 repo：
   最簡單的方式是在 repo 頁面點 **Add file → Upload files**，把整個資料夾內容拖進去。
   如果你比較熟悉 git，也可以直接 `git init && git add . && git commit -m "init" && git push`。
3. 進到 repo 的 **Settings → Pages**，「Source」選 **Deploy from a branch**，
   Branch 選 `main`（或你上傳時的分支）、資料夾選 `/ (root)`，存檔。
   等 1-2 分鐘，GitHub 會給你一個網址，長得像：
   `https://levis50192-cmyk.github.io/bingo-analysis/`
4. 進到 repo 的 **Actions** 分頁，應該會看到「更新賓果賓果開獎資料與統計」這個 workflow。
   第一次可以手動點右邊的 **Run workflow** 觸發一次，確認它能成功抓到資料、綠勾勾代表成功。
   之後就會照排程（每 15 分鐘）自動執行，完全不用管它。
5. 把步驟 3 拿到的網址加到手機主畫面（Safari／Chrome 分享選單裡的「加入主畫面」），
   之後想看的時候直接點主畫面圖示即可，不用開 Claude。

## 之後想調整排程頻率

打開 `.github/workflows/update.yml`，把 `cron: "7,22,37,52 * * * *"` 改成你要的間隔即可，
例如 `*/30 * * * *` 是每 30 分鐘（記得盡量避開整點/整 15 分這種大家都愛用的時間點，
錯開幾分鐘比較不會被 GitHub 延遲或跳過）。**不建議設太密**（例如低於 5 分鐘），GitHub
對高頻率排程本來就會自動延後執行，設太密也沒有實際效果。

## 關於這些數學方法（誠實檢查表）

每個方法在程式碼裡都有自己的 `field` 欄位，標示它實際對應的學門，不是隨便貼標籤：

- 頻率法 → 統計學（經驗次數估計）
- 遺漏值法 → 機率論（幾何分布，順便示範「賭徒謬誤」不管用）
- 卡方均勻性檢定 → 統計學／精算學（誠實檢查資料是否真的均勻隨機，本身不是選號方法）
- 貝氏後驗機率法 → 機率論／精算學（Beta-Binomial 模型）
- 共現矩陣法 → 代數（矩陣列總和，嚴格說只能算矩陣統計，稱不上線性代數）
- 綜合建議 → 把前 4 種方法的排名做百分位平均，不是第 5 種更準的方法
- 蒙地卡羅模擬對照 → 電腦模擬統計（之前標成「空間幾何統計」其實不準確，這裡已經改回誠實的標法）
- **空間自相關法（Moran's I）** → 真正的空間幾何學／空間統計：把 01~80 依賓果賓果選號盤常見的
  10欄×8列排列成座標，計算 Moran's I 空間自相關指數，檢定熱門號在盤面上是否聚集，並用排列檢定
  算出 p 值。這是貨真價實的空間統計方法，但誠實地說：開獎本身沒有空間概念，這個檢定「應該」
  顯示沒有聚集才是正常結果。
- **共現矩陣譜分析（特徵值分解）** → 真正的線性代數：對共現矩陣做特徵值分解（power iteration，
  不依賴 numpy），找出矩陣的主要結構模式。這是原本共現矩陣法沒做到的「真代數」部分。

這兩個新方法一樣會被拿去跟其他方法一起回測、一起跟純亂猜基準線比較，不會因為公式聽起來
更厲害就得到特殊待遇——這就是這個工具存在的意義：讓你自己親眼確認，不管用哪種數學工具，
長期命中率都會收斂到跟亂猜差不多。

## 誠實聲明（沿用原本立場，沒有改變）

BINGO BINGO 是每期獨立、電腦亂數產生的抽獎，不存在任何數學方法能讓「下一期」的預測準確率
超越均勻亂猜。這個工具的「建議號碼」只是把各種統計/機率方法整理成可以互相比較、並誠實回測
命中率的儀表板，用來證明「長期下來所有方法都會收斂到跟亂猜差不多」這件事，不是中獎預測。
BINGO BINGO 的獎金結構是負期望值，請理性消費、量力而為。
